=== Terminology ===

cone mode: 用于指定所需的文件子集的两种模式之一。
	在锥形模式下，用户指定了目录（获得该目录下的所有文件以及前导目录中的所有文件）。
	而在非锥体模式下，用户指定 gitignore 风格的模式。 受控于
	由 sparse-checkout init|set 的 --[no-]cone 选项控制。

SKIP_WORKTREE: 当被追踪的文件不符合稀疏规范并从工作树中被删除时，
	索引中的文件会被标记为 SKIP_WORKTREE 位。
	注意，如果一个被追踪的文件有 SKIP_WORKTREE 位，
	但该文件后来还是被用户写入了工作树中, SKIP_WORKTREE 位会在任何
	Git 操作开始时被清空。

	大多数稀疏签出的用户都不知道这个实现细节，
	因此在面向用户的描述和命令标志中一般应避免使用该术语。
	不幸的是，在 `sparse-checkout` 子命令之前，这个低层次的细节是暴露的。
	在写这篇文章的时候，仍然在不同的地方暴露出来。

sparse-checkout: git中的一个子命令，用于将工作树中的文件减少到所有被追踪的文件的子集。
	工作树中的文件减少到所有被追踪文件的一个子集。 另外， 在$GIT_DIR/info 目录下的
	sparse-checkout 文件，用于跟踪与用户所需的子集。

sparse cone: 查看 cone mode

sparse directory: 在索引中对应于一个目录的条目，而不是在索引中展示该目录下的所有文件。
	你也可以看看 sparse-index。 一些可能引起混淆的事情是 "稀疏目录" 并不符合
	稀疏检出规则（也就是目录不出现在工作树上） 将来可能会被重新命名（例如，"skipped	directory"）。

sparse index: 稀疏检查的一种特殊模式，通过记录一个目录条目来代替该目录下的所有文件，使索引变得稀疏。
	（从而使其成为一个 "跳过的目录"，不幸的是，它也被称为 "稀疏的目录"），
	并且对可能的多个目录。 这是由init|set|reapply --[no-]sparse-index 选项来控制的。

sparsity patterns: 来自 $GIT_DIR/info/sparse-checkout 的模式，用于定义感兴趣的文件集。
	一个警告。这很容易让人过度使用这个术语（或缩短的 "pattern"术语），原因有两个
	(1) 用户在锥形模式下指定目录而不是模式（他们的目录被转换为模式，但如果你使用 "模式 "一词，
	用户可能会认为你在谈论非锥体的词 “pattern”），(b) 稀疏规范 sparse specification
	可能会在工作树或索引中暂时与稀疏模式 sparsity patterns 不同
	（见 "Sparse specification vs. sparsity patterns"）。

sparse specification: 稀疏的规范。用户关注区域内的路径集合。 这
	通常只是符合稀疏模式的跟踪文件。但稀疏规格可以暂时不同，包括其他文件。
	（见 "Sparse specification vs. sparsity patterns"）

	* 当用历史记录工作时，稀疏规格正好是稀疏规格正是与稀疏模式相匹配的文件集。
	log revision -> sparse specification == sparsity patterns

	* 当与工作树交互时，稀疏的规格是与稀疏模式相匹配的文件集。
	  是 SKIP_WORKTREE 位为 0 的跟踪文件的集合以及是工作树中被跟踪文件。
	work tree -> sparse specification == files(SKIP_WORKTREE & file.bit == 0) || tracked(files in worktree)

	* 当修改或显示来自 index 的结果时，稀疏规范是 SKIP_WORKTREE 位为 0 的被追踪文件的集合或在 index 中与 HEAD 不同的文件。
	index -> sparse specification == files(SKIP_WORKTREE & file.bit == 0) || file.diff(index, HEAD)

	* 如果使用索引和工作副本，稀疏的规格是索引和工作副本的路径的结合。

vivifying: 当一个命令将一个被追踪的文件恢复到工作树上时（并且
	希望也能清除该文件索引中的 SKIP_WORKTREE 位) 这被称为 "激活 "该文件。

=== Behavior classes ===

从上面来看，有几类行为。

  * "restrict"

    这一类的命令只读写工作树上的满足稀疏规范内的文件。

    当转移到一个新的提交时（例如 switch，reset --hard），这些命令
    可能会在操作开始时更新稀疏规范之外的索引文件，但在操作结束时，
    这些索引文件将再次与 HEAD 匹配，因此这些文件将再次在稀疏规范之外。

    当路径被明确指定时，这些路径与稀疏规范相交，并且只对这些路径进行操作。
    (例如，"git restore [-staged] -- '*.png'"，"git reset -p -- '*.md'")

=== Sparse specification vs. sparsity patterns ===

在一个良好的情况下，稀疏规范直接由稀疏规范由 $GIT_DIR/info/sparse-checkout
文件直接给出。 然而，它可能会暂时性地分歧，原因有几个。

    * 需要解决冲突（合并会使有冲突的文件存活）。
    * 运行隐含激活文件的 Git 命令（例如 "git stash apply"）。
    * 运行显式激活文件的 Git 命令（例如 "git checkout --ignore-skip-worktree-bits FILENAME")
    * 写入这些文件的其他命令（可能是用户从其他地方拷贝过来的）。

对于最后一项，请注意我们会自动清除存在于工作树中的文件的 SKIP_WORKTREE 位，。 自82386b4496以来，这一直是真的
("Merge branch 'en/present-despite-skipped'")，从82386b4496开始就是如此。
2022-03-09)

然而，这种情况是短暂的，因为:

   * 这种暂时性的差异可以而且会被自动消除，因为
     调用unpack_trees()的命令的一个副作用（checkout,
     merge，reset，等等）。
   * 用户也可以通过以下方式要求纠正这种暂时性的差异
     运行 `git sparse-checkout reapply`。 许多地方推荐
     运行该命令。
   * 我们也欢迎其他命令来隐含地修复这些差异；
     我们可能会在未来增加更多的命令。

虽然我们避免丢弃未缓存的修改或有冲突的文件。
否则我们会积极地尝试修复这些短暂的差异。 如果
用户希望这些差异持续存在，他们应该运行 `git sparse-checkout'的
`set` 或 `add` 子命令，以反映他们想要的稀疏规范。

然而，当我们需要对历史进行查询时，仅限于"相关的文件子集" 时，这样一个临时扩展的稀疏规范被忽略了。
这有几个原因:

   * 当做类似以下事情时，想要的行为
	 git grep expression REVISION
     这样的行为，大致上是用户希望从
	 git checkout REVISION && git grep expression
     (再加上一个 "REVISION: "的前缀)，这有几个影响。

   * REVISION 可能有不在当前索引中的路径，所以没有
     我们可以参考这些路径的 SKIP_WORKTREE 设置。

   * 由于`checkout`是一个试图消除
     疏散规范中的瞬时差异，所以有必要
     使用校正后的稀疏规范
     (即$GIT_DIR/info/sparse-checkout)而不是试图 试图查阅SKIP_WORKTREE。

因此，暂时扩大（或限制）的稀疏规范适用于
工作树，但不适用于历史查询，在历史查询中我们总是使用
稀疏模式。 (参见[16]关于这个问题的早期讨论）。

类似于基于工作树中存在的额外文件的瞬时扩展稀疏规范，我们也需要
考虑在索引中被修改的额外文件。 特别是。

稀疏模式相匹配的文件，并且该文件不存在于工作树中，我们仍然要考虑该文件的
树中，当我们专门执行一个与索引相关的查询（例如，git
diff --cached [REVISION], git diff-index [REVISION], git restore --staged
--source=REVISION -- PATHS，等等）我们仍然希望考虑该文件是稀疏规范的一部分
